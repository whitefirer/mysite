## 现象

在本地开发环境（TenBox VM）里，网页应用的上传功能有个诡异规律：

- **小图（几 KB）：秒传成功**
- **稍大一点的图（几百 KB）：前端等 60-120 秒超时取消，服务端日志显示请求处理了约 5 分钟（300 秒）后返回 200，但素材库看不到图**
- 用 `localhost` 访问一切正常，用局域网 IP（`192.168.0.102`）访问必现
- 上传链路本身没问题——同样的请求换个浏览器测试工具就秒过

"稍大图从没成功过，只有小图成功过"——这个历史规律是整件事最重要的线索，可惜一开始没当回事。

## 排查历程

### 第一幕：怀疑应用层（sharp 图片处理）

最初看到"服务端处理 5 分钟"，第一反应是图片处理库 sharp（libvips）在虚拟机环境下的病理性慢路径。代码里明明有 15 秒超时保护，但注释写着"超时不取消底层操作"——如果 sharp 原生调用阻塞了事件循环，连超时定时器都跑不了，请求挂 5 分钟完全说得通。

于是做了"快路径"：AI 封面这种浏览器自产的 PNG 跳过 sharp 重处理，直接 magic bytes 鉴型 + 读 PNG 头 + 哈希。**结果还是挂 5 分钟**——sharp 假说排除。

### 第二幕：怀疑浏览器差异

用 playwright 的 Chromium 测试全部正常（几十毫秒），但用系统安装的 Chromium 复现出了异常——一度以为是浏览器 multipart 编码差异。为此把 multipart 解析从 Node 内置的 `req.formData()` 换成了 busboy 手动解析。**结果依然挂**——解析器假说排除。

### 第三幕：打点定位，矛头转向传输层

在路由入口加打点日志，发现关键事实：

```
[upload] 进入 route cl=437671   ← 请求到达了，content-length 正常（437KB）
（然后没有任何后续打点）          ← 卡在读取请求体
```

**请求体（body）的 TCP 传输本身就没有完成**——服务端在等一个永远传不完的 body，300 秒是 Node 的固定超时。

### 第四幕：网络层实锤（当时的结论）

用 curl 直接做传输实验：

```
localhost POST 500KB   → 46ms 完成
192.168.0.102 POST 500KB → 30 秒超时卡死
```

然后测出精确阈值：

```
256KB → 35ms 秒过
300KB → 卡死
```

这台开发机是 TenBox VM（自研 C++ VMM，宿主机是 Windows，走 WHVP 后端），virtio-net 后端接自研 lwIP 用户态 NAT（`10.0.2.15`，网关 `10.0.2.2`），guest 的 TCP 流量纯软件转发。当时能坐实的结论是：**VM 用户态网络路径对超过 ~256KB 的连续 body 传输存在缺陷**——TCP 发送窗口不增长，连接挂起约 300 秒。具体坏在栈的哪一层，当天没有继续往下挖。

为什么小图能过？小 body 落在单个 TCP 窗口内，一次发完不触发缺陷路径。

为什么 localhost 正常？localhost 走回环接口，完全不经过 VM 网络栈。

## 应急方案：应用层分块上传

网络层的根治当时判断要动 VM 网络配置，风险收益比不划算。于是从应用层绕开：

- **前端**：文件切成 **128KB/块**（远低于 256KB 阈值）顺序上传
- **服务端**：分块端点按会话收集，收齐后拼接，走原有处理流程（图片处理/去重/素材建档）
- **全入口接入**：封面选择器、编辑器粘贴/拖拽、头像上传、内容工作室——所有上传路径统一走分块工具

实测结果：**卡死的网络路径上，437KB 封面上传从 300 秒挂起变成 1.6 秒完成**。

## 终局：真根因与根治（2026-09-17）

一个月后，这个缺陷才被重新捡起来做对照实验——隔这么久的原因很朴素：分块上传上线后上传功能一直好用，当时手头没空、也没有什么迫切需求去动网络层。直到共享存储池（JuiceFS→RustFS）落地，VM 网络从"开发便利性"变成了"生产热路径"，缺陷的影响面跟着变了，才重启调查——结论推翻了"TCP 栈缺陷"的当日判断。

**对照实验**：同一套代码，Windows/WHVP 生产端稳定复现（宿主 curl 打转发端口：200KB 秒过、500KB 挂满超时、服务端永远读不满 body、连接悬尸）；**KVM 后端完全不复发**——v0.8.1 与 v0.8.2 两个版本、loopback 与跨机 LAN 两种拓扑、256KB→50MB 全档位含并发全部秒过。缺陷是平台相关的，这指向虚拟化后端之下的事件层，而不是与平台无关的 TCP 栈逻辑。

**真根因**：VM runtime 的 socket 事件层——libuv 的 fd 复用竞态导致 poll 注册丢失：socket 关闭后 fd 被内核快速复用，事件循环里旧 fd 的 poll 注册没挂到新 fd 上，于是"socket 明明有数据可读，事件循环却永远收不到通知"，连接挂起。Windows 上 libuv 走 wepoll，其 fd 分配与注册时序才让这个竞态显现；KVM 后端的时序不同，即便带病的 0.8.1 也不显现。lwIP 栈本身全程是清白的。

**上游修复**：0.8.1（延迟 close，避免 fd 被立即复用）+ 0.8.2（watchdog：检测到"有未读字节但 1 秒无进展"时重挂 poll）。

**根治验证**：Windows 宿主把 `tenbox-vm-runtime` 换成 0.8.2+ 并重启 VM 后，同一拓扑 200KB/500KB/10MB 全部秒过；LAN ranged GET 500 连发 0 stall（旧基线 1 stall/500）；对象存储上下行恢复对称 ~30 MiB/s（原 3.2/31 畸形）。**Windows 宿主升级 runtime 到 0.8.2+ 即根治，网络栈无需更换。**

## 经验教训

1. **"小文件能传大文件不能"是最有价值的线索**——它直接指向传输层而非应用层。如果早做阈值实验，能省掉两轮应用层排查
2. **next dev 的请求日志只在响应完成后打印**——挂起的请求在日志里不可见，必须自己在路由入口加打点
3. **打点要打在"进入"位置**：入口打点证明"请求到达了"，后续打点缺失才能定位"卡在哪一步"。这次正是 `[upload] 进入 route` 出现而后续打点全部缺失，才把矛头从 sharp 转向 body 传输
4. **localhost 正常 ≠ 局域网 IP 正常**：本机回环路径绕开了很多网络栈问题，测试一定要覆盖真实访问路径
5. **应用层绕开 vs 网络层治本**：分块上传是"绕过缺陷"而非"修复缺陷"，作为应急是对的；但应急方案上线不该是终点，缺陷要留档追踪
6. **根因没坐实前，别急着给它起名字**：第一轮的排查笔记凭"VM + hostfwd 卡死"的症状就把锅记到了"QEMU/slirp"头上——实现都没读过。这个错误标签在后来的讨论里活了很久，直到读代码才发现栈是自研 lwIP、真凶在事件层。**涉及具体实现的论断，先读代码再开口**

## 附：网络层后续路线（2026-09-17 重写）

缺陷已根治，但存储池落地后暴露的其余网络诉求还在：hostfwd 入向连接下载方向慢（曾实测 0.83MB/s vs 上传 26MB/s，runtime 修复后待复测）、双 VM 各自在 NAT 后 tailscale UDP 打洞失败（全程走 DERP 中继——这点对任何 NAT 后端都成立，换栈不治）、每个新服务端口要手工加转发。后续分三阶段，每阶段独立可交付：

### 阶段一：可选的替代 NAT 后端（治慢，治余量）

[gvisor-tap-vsock](https://github.com/containers/gvisor-tap-vsock)（gvproxy）：gVisor 的用户态 TCP/IP 栈，**免驱动、免特权**，ICMP 可用、UDP 可靠、吞吐高一个量级（Lima/Podman machine/crc 的生产选择）。TenBox 接法：virtio-net 设备的以太帧流从内置 lwIP 后端改道 gvproxy 的 QEMU 兼容 socket（`--listen-qemu`——这名字只是协议的历史由来，承载的是带 4 字节长度头的原始以太帧，不依赖 QEMU 本体）。设计上与 lwIP 后端共存、按 VM 可选，不替换。备选还有 libslirp（嵌入式 C 库，模型同构）与 passt（性能更好但仅 Linux，三平台需求下出局）。验证目标：吞吐基线 + 存储池场景实测 + 控制 API 行为。

### 阶段二：端口转发的自动化（治"手动开端口"）

NAT 模式下入向总要转发，两层缓解，且都不依赖阶段一：

- **用好现有的热更新**：TenBox 的 hostfwd 已支持运行中动态改（`vm.edit` 下发 `host_forwards` patch，runtime 侧即时生效）——缺的是顺手的入口（GUI 一键、服务上线自动注册），不是栈能力
- **范围转发**：一条规则转一段（如 `30000-32000`），把"每个工作台/服务加一条"的日常操作一次性消掉
- **若上 gvproxy**：其 HTTP 控制 API 可实现 VM 内新监听端口自动建转发，"手动"二字彻底消掉

### 阶段三：bridged 可选后端（治概念，但分层）

TAP/bridge 让 VM 拿真 LAN IP，**端口转发概念消失**，tailscale 直连也随之解锁。但它和 TenBox 的沙盒定位有张力，正确姿势是把网络暴露做成沙盒策略的显式维度：

- **离线 / NAT（默认）/ Bridged（opt-in）** 三档；bridged 配 guest 防火墙默认拒入 + UI 明示"对局域网可见"
- 用法分野：**agent 沙盒 VM 永远 NAT/离线；自己的基础设施 VM（存储、服务节点）才 bridged**——同一套定位，两类负载各取所需
- Windows/WHVP 下的桥接不走 TAP 驱动老路（兼容性差），走 Hyper-V 可扩展交换机或 packet filter，细节待 spike
